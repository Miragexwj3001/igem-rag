# iGEM RAG 消融实验与 Baseline 对比报告

**日期**：2026-04-26  
**数据集**：387 道题（规则化 187 + LLM生成 200）  
**评估范围**：纯检索质量（不含生成），Top-10 召回  
**基线系统**：Hybrid BM25+FAISS + CrossEncoder Reranker, recall=50  

---

## 实验目的

量化混合检索系统中各组件的实际贡献，回答以下问题：

1. BM25 与向量检索（FAISS）各自的能力上限是多少？
2. CrossEncoder Reranker 贡献了多少提升？
3. 年份硬过滤对召回率的影响有多大？
4. 召回候选数（recall_candidates）对性能的影响如何？

---

**检索流程**（当前系统）：

```
BM25 召回 (Top-K)        FAISS 向量召回 (Top-K)
       ↓                        ↓
       ↓_____ 合并去重 ___________↓
                   ↓
          年份硬过滤（可选）
```

**运行环境**：`igem-rag` conda 环境，CPU-only（RTX 5090 与 torch 2.3.1 不兼容），脚本 `eval/run_ablation.py`。

## 发现与分析

### 1. BM25 远强于纯向量检索（B1 vs B2）

| | Hit@5 | MRR |
|---|:---:|:---:|
| BM25 Only (B1) | 0.643 | 0.544 |
| Dense Only (B2) | 0.481 | 0.405 |
| **差距** | **+0.162** | **+0.139** |

BM25 在规则化题上优势尤为突出（Hit@5：0.636 vs 0.353），差距高达 **28pp**。原因：iGEM wiki 内容关键词密度高，队名、年份、生物术语等精确词匹配优势显著；而向量模型难以区分不同年份同一队伍的语义相似内容。

LLM 生成题上两者差距缩小（0.650 vs 0.600），因为 LLM 题不含队名/年份，语义匹配更有价值。

### 2. CrossEncoder Reranker 是最重要的组件之一（B0 vs B3）

| | Hit@1 | Hit@5 | MRR |
|---|:---:|:---:|:---:|
| 有 Reranker (B0) | **0.470** | **0.669** | **0.551** |
| 无 Reranker, RRF (B3) | 0.284 | 0.556 | 0.396 |
| **差距** | **+0.186** | **+0.113** | **+0.155** |

Reranker 对 **Hit@1 影响最大**（+18.6pp），说明正确答案经常被召回但排序靠后；CrossEncoder 将其提升到首位。MRR 差距（+15.5pp）也印证了这一点。规则化题受益最大（Hit@1：0.449 vs 0.166）。

### 3. 混合检索优于单路（B0 vs B1/B2）

| | Hit@5 | MRR |
|---|:---:|:---:|
| Hybrid B0 | **0.669** | **0.551** |
| BM25 Only B1 | 0.643 | 0.544 |
| **差距** | **+0.026** | **+0.007** |

相比 BM25 单路，Hybrid 在 Hit@5 上提升约 **2.6pp**，提升幅度不大但稳定。FAISS 向量召回在 LLM 生成题中贡献更明显，能捕捉 BM25 漏掉的语义相关内容。

### 4. 年份硬过滤对精确匹配至关重要（B0 vs A1）

| | Hit@5（整体） | Hit@5（规则化题） | Hit@5（LLM生成题） |
|---|:---:|:---:|:---:|
| 有年份过滤 (B0) | **0.669** | **0.658** | **0.680** |
| 无年份过滤 (A1) | 0.636 | 0.588 | 0.680 |
| **差距** | **+0.033** | **+0.070** | 0.000 |

年份过滤对 **规则化题**（含团队+年份的精确查询）影响显著（+7pp），但对 LLM 生成题无影响（这类题不含年份，过滤不介入）。另外关闭年份过滤后耗时更长（+332s），因为 CrossEncoder 需要处理更多候选。

### 5. recall=50 是效率最优配置（A3a vs B0 vs A3b）

| | Hit@5 | MRR | 耗时 |
|---|:---:|:---:|---:|
| recall=20 (A3a) | 0.636 | 0.540 | 560s |
| recall=50 (B0) | **0.669** | **0.551** | 1740s |
| recall=100 (A3b) | **0.669** | 0.545 | 2607s |

recall=100 与 recall=50 在 Hit@5 上持平（均为 0.669），但耗时多 50%（2607s vs 1740s）。recall=20 在规则化题上有明显损失（Hit@5 下降 5.4pp）。**recall=50 是精度与速度的最优平衡点**。

## 结论

### 各组件贡献排序

```
CrossEncoder Reranker  >  BM25 稀疏召回  >  年份硬过滤  >  FAISS 向量补充
     +11.3pp Hit@5          核心支柱           +3.3pp        +2.6pp
```

### 当前系统的合理性验证

- 当前 recall=50 配置是经验最优，无需调整
- CrossEncoder 和 BM25 是核心组件，不可省略
- 年份过滤逻辑对精确查询贡献显著，应保留

### 后续优化建议

1. **提升 BM25 或换更强的稀疏检索**：BM25 是最重要的召回路径，可尝试 BM25+ 或 SPLADE 等稀疏模型
2. **更换向量模型**：`bge-large-zh` 替代 `bge-base-zh` 可能对语义召回（特别是 LLM 生成题）有帮助，但需重建索引
3. **加强精确排序**：Hit@1 = 0.470 仍有较大提升空间，可尝试更强的 Reranker（如 `bge-reranker-large`）
4. **针对弱点子模块**：输入参数与假设（Hit@5=0.364）等同质化严重的子模块，考虑在 chunk 文本中增强团队/年份标识权重，提高区分度
